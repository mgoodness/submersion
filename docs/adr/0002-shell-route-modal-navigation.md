# Routes reachable from a dialog need an explicit root parentNavigatorKey

go_router's `ShellRoute` gives every nested child route a page in the shell's own nested navigator, not the app's root navigator, unless the route declares `parentNavigatorKey`. This is invisible for routes only ever reached through normal in-shell navigation, but it breaks the moment a route can also be reached from inside a `showDialog` (default `useRootNavigator: true`) or a `showModalBottomSheet` stacked on that dialog: the dialog/sheet render on the root navigator, while the pushed route mounts on the shell's nested navigator underneath it. The push succeeds and the page builds, but it's invisible until the dialog/sheet are dismissed.

The fix is to give any such route `parentNavigatorKey: rootNavigatorKey` so it always mounts on the root navigator, matching wherever an enclosing dialog/sheet actually is. This is the standard go_router pattern for "routes that need to appear over the shell's chrome" (`/welcome` uses the same escape by living outside the `ShellRoute` entirely). `newBuddy` (`app_router.dart`) is the first route in this codebase to need it, because it's the only one currently reachable from within `BuddyPicker`'s "Add New Buddy" flow, itself sometimes opened inside a bulk-edit dialog (issue #707, PR #708).

A related, easy-to-misdiagnose behavior: pushing a fully-opaque route (any `MaterialPageRoute`/GoRoute page) over an already-open `showDialog`/`showModalBottomSheet` on the *same* navigator elides that dialog/sheet from the widget tree while it's covered — `find.byType`/visual inspection will show it gone. This is not a pop: confirmed via a `NavigatorObserver`, no `didPop`/`didRemove` fires, the route stays in the navigator's history, and it reappears with its state fully intact as soon as the covering route is popped. Don't "fix" this by routing around go_router (e.g. an imperative `Navigator.push` bypassing it) — that's unnecessary and throws away the benefits of a named go_router route for no reason.

## Considered options

- **Push `newBuddy` via a raw imperative `Navigator.of(context, rootNavigator: true).push(MaterialPageRoute(...))`, bypassing go_router entirely** — initially tried after mistaking the harmless dialog-elision behavior above for a destructive eviction bug. Rejected once a `NavigatorObserver` proved the dialog/sheet were never popped: the simpler `parentNavigatorKey` fix works and keeps `/buddies/new` a real, uniformly-reachable named route.
- **Scope the `parentNavigatorKey` fix to only the bulk-edit call site** — not possible; `parentNavigatorKey` is a property of the route, not the caller, so it necessarily applies to every path that reaches `newBuddy` (bulk-edit dialog, embedded single-dive-edit picker, `BuddyListPage`'s own "Add Buddy" button). Verified all three still work correctly.
